# Engineering standards

Language-neutral standards for every app the studio builds. The app's own conventions (naming, folder layout, error style, test style) win over a preference of yours; where the app has none, use these. Language specialists add idiom, never contradict this file.

## Code

- **Public APIs are documented.** Every public type, function, endpoint, command and configuration key says what it does, its inputs and outputs, its errors, and its side effects, in the language's doc-comment form. Comments elsewhere explain why, not what.
- **Data-driven configuration.** Values that tune behavior (limits, timeouts, URLs, feature flags, thresholds, copy) live in configuration or data files, not scattered literals. Per-environment values come from the environment, not from code branches.
- **Dependency injection over singletons** where it makes code testable: pass in clocks, file systems, network clients, stores and random sources. A singleton is acceptable for genuinely process-wide resources (logger, app root), behind an interface.
- **Errors are handled deliberately.** No empty catch blocks, no swallowed errors. Distinguish expected failures (bad input, offline, not found) from bugs. Return or throw typed, actionable errors; show the user a plain message and a next step; log the detail. Fail closed on security errors. Every external call has a timeout and a failure path.
- **Logging without secrets or PII.** Log events with enough context to diagnose (IDs, states, durations), at sensible levels. Never log credentials, tokens, keys, full request bodies with personal data, or raw user content. Redact at the logging layer. Logs are not an analytics system.
- **Security defaults.** Validate and encode all input from outside the process; least privilege for processes, tokens and permissions; secrets from the environment or the platform's secure store, never in source; parameterized queries; current, maintained dependencies, audited when changed; secure transport; no custom cryptography. Review for the OWASP Top 10 (ASVS for services, MASVS for mobile) as relevant.
- **Accessibility and localization from the start.** Every control has a name, role and keyboard path; contrast and text scaling are respected; nothing is conveyed by color alone. User-facing strings are externalized from day one, never concatenated; dates, numbers and plurals use locale-aware formatting; layouts survive longer text and right-to-left. Retrofitting costs more than starting right.
- **Performance budgets.** Any app with a user-facing latency or footprint has budgets (startup, interaction latency, memory, bundle or binary size, battery, request time) in `perf-budget.md`, measured on the lowest supported device or a representative build. A change that blows a budget is a defect.
- **Compatibility.** Saved data and public APIs are backward compatible. Old files, databases and settings open in the new build; a migration is forward-safe, tested on a copy, and reversible or backed up. Public API changes are additive; breaking changes are versioned, announced and given a deprecation window. Data written by a newer version is not destroyed by an older one.

## Process

- **Conventional Commits with story IDs.** `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, `perf:`, `build:`, `ci:`. The subject is imperative and short; the body says why and carries the story or requirement ID (`Story: <epic>/story-012`, `Refs: REQ-<feature>-003`). Commit only when asked.
- **Small, reviewable changes.** One purpose per change. No drive-by reformatting, no unrelated renames. A change that cannot be reviewed in one sitting is split. Keep the build green between steps.
- **Prototypes never imported by production code.** Prototypes live in `prototypes/<name>/` with a README (hypothesis, how to run, status, findings), may be sloppy, and never modify files outside their folder. A successful prototype is rewritten to production standards, never migrated. Time-box spikes to about two days; longer work is a planned story.
- **Generated files are never hand-edited.** Change the source or the generator and regenerate. Generated files are marked in a header or `.gitattributes` (`linguist-generated`), and their generator command is documented. Lockfiles are changed by the package manager only.
- **Pin and verify.** Versions of runtimes, SDKs and key libraries are pinned (`stack-reference.md`). Check an API against the installed version or the official docs before using it; training data goes stale.
- **Delete, do not comment out.** Version control remembers. Dead code, unused flags and stale TODOs without an owner are removed or filed.

## Per-layer guidance

**UI code.** No business logic in views; views render state and emit intents. All strings from the localization layer; all colors, spacing and type from design tokens, not literals. Every state is designed: loading, empty, error, offline, partial, long text, permission denied. Respect system settings (theme, text size, reduced motion, high contrast). Keyboard and screen-reader paths work. Never block the UI thread. UI changes are run and looked at (`testing.md`).

**Stable layout: every element has a home, and nothing else can move it.** Each element's position is defined against its container (the window, a panel, a dialog, a row), by edge, alignment or grid column, never by "after whatever came before it" when that something can appear, disappear or change size. The goal is that things in the UI stay where they are supposed to be regardless of display scaling, resolution, screen size, window size, language or text length, and regardless of dynamic content: warnings, validation messages, notes, counters, "copied" confirmations and optional buttons coming and going.
- Groups are placed from their own anchor: a right-aligned group (Cancel/Send) from the container's right edge, a left group from the left edge, a centered element from the center. One group's width never decides another group's position.
- Transient elements get a reserved slot of fixed size, or live in a region (a scrolling body, an overlay, a tooltip) that cannot push anything else. Optional buttons that appear and disappear sit at the outer end of their own group, so their presence never shifts a neighbour; or they stay visible and become disabled.
- When the container resizes or the scale changes, elements keep their anchor and margins; only the flexible region (a text area, a list) grows or shrinks.
- Tests: for every screen and dialog, assert that each anchored control's position relative to its anchor is identical with and without each transient element, at the minimum and default window sizes, and at 100%, 125%, 150% and 200% scaling.
Applies to every platform and toolkit; it is a default from the first line of UI code, not a fix applied after someone notices.

**API and network code.** The contract (`api-contract.md`) comes first and is the source of truth. Validate at the boundary; return consistent, typed errors (for example RFC 9457 problem details); paginate collections; make mutating calls idempotent or give them idempotency keys; version the API. Clients set timeouts, retry with exponential backoff and jitter only on safe operations, and handle offline. Authenticate and authorize every request server-side; never trust the client. No secrets in URLs. Contract tests guard compatibility.

**Data and migrations.** Schema changes are migrations in version control, never manual edits. Migrations are idempotent where possible, tested on a copy of realistic data, and ordered. Prefer expand then contract: add the new shape, dual-write or backfill, switch readers, remove the old shape in a later release. Document rollback or the backup taken. Index for real queries; keep transactions short; protect integrity with constraints. Local and file formats carry a version number. Never run a migration against real user data without the user's yes and a backup.

**Infra code.** Declarative and in version control (containers, compose files, IaC). Idempotent and re-runnable; plan or diff before apply. No manual changes to running systems that are not captured back into code. Least privilege for every identity. Secrets from a secrets manager. Pin image and provider versions. Every deployment has a health check and a rollback. Infrastructure facts (hosts, ports, routes) come from the infrastructure record, not memory, and changes are written back to it.

**Build files.** Reproducible: pinned toolchain, committed lockfile, no network fetches of unpinned code at build time. One documented command each for build, test, lint, format and run (the `commands` in `studio.yaml`). Version stamping is automatic. Warnings are errors in CI where the toolchain allows. Build scripts work on the platforms the team builds on, and do not assume a particular shell. Signing keys are held by the CI secret store or the platform keychain, never in the repo.
